# CLAUDE.md

Сервис лояльности поверх Syrve Cloud API: Telegram-бот для гостя + веб-админка. Тестовое задание на один день. Полный план и архитектура — `PLAN.md`.

## Приоритеты

1. Обязательная часть (О1–О6 в PLAN.md) работает end-to-end.
2. Простота важнее «продакшн-архитектуры». Не добавлять слои, паттерны и библиотеки вне стека ниже без моего согласия.
3. Не реализовывать функции, которых нет в текущей задаче. Кажется, что что-то нужно, — спроси.

## Стек (фиксирован)

NestJS + TypeScript, class-validator (DTO), zod (только `.env`), Prisma + PostgreSQL, Redis + BullMQ (`@nestjs/bullmq`), grammY, `@nestjs/jwt` + `crypto.scrypt`, Jest, React + Vite, nginx, Docker Compose.

## Правила

- Вся работа с Syrve — только через `SYRVE_CLIENT` из `SyrveModule`. Нигде больше нет HTTP-вызовов к Syrve.
- Бот и контроллеры тонкие: только ввод/вывод, логика в сервисах.
- Источник правды по балансу и транзакциям — Syrve. Не хранить баланс в нашей БД.
- Списание: всегда проверять баланс до `chargeoff` (Syrve пускает в минус).
- Баланс гостя — только кошелёк `SYRVE_WALLET_ID` из `walletBalances`, не первый в списке.
- Начисление / списание: **сначала** `Operation` со статусом `PENDING` (уникальный `idempotencyKey`), **потом** вызов Syrve, затем `SUCCESS` / `FAILED` / `UNKNOWN`. Конфликт ключа = повтор запроса, Syrve второй раз не вызывать.
- Повтор HTTP-запроса к Syrve — только после 401 с новым токеном. Таймаут и сетевые ошибки **не повторять**: `topup` / `chargeoff` могли уже примениться → статус `UNKNOWN`.
- Уведомления: только транзакции с нашим `walletId` и `sum !== 0`; все страницы `by_revision`; `lastRevision` обновлять после постановки всех уведомлений в очередь; дедуп — `jobId = txId` + таблица `NotifiedTransaction`.
- Интерфейс `SyrveClient` повторяет реальные методы API (см. PLAN.md → «Syrve за интерфейсом»), а не скрывает их за одним «createCustomer».
- Телефон нормализуется в `+380XXXXXXXXX` через `common/phone.ts`.
- Секреты только из `.env` через `ConfigModule`. Никаких секретов в коде, логах и `docs/`.
- Ошибки Syrve логировать с `correlationId`. Пользователю и в публичные эндпоинты (включая health) — понятный нейтральный текст на украинском, без внутренних деталей.
- Авторизация админки: `@nestjs/jwt` в httpOnly cookie (`sameSite=lax`, `secure` в production), пароль — `crypto.scrypt`. Без bcrypt.
- Тексты для пользователя (бот, админка) — на украинском.
- Миграции только через `prisma migrate`. Не править применённые миграции.

## Процесс

- Каждый этап (О1–О6, Д1) — в отдельной ветке `feat/<этап>` от `main`. Merge в `main` — через PR после ревью.
- Перед кодом — короткий план изменения, жди моего «ок».
- Одна задача — один коммит с понятным сообщением (Conventional Commits: `feat:`, `fix:`, `test:`, `docs:`, `chore:`).
- После изменения: `docker compose up --build` поднимается и затронутый сценарий работает.
- Не трогай файлы вне текущей задачи.
- Ревью каждой ветки делает Codex по правилам из `AGENTS.md`. Его замечания либо исправляем, либо объясняем, почему нет.

## Тесты

- Jest, только unit-тесты на критичную логику — не на всё подряд:
  - проверка баланса перед списанием;
  - фильтр транзакций для уведомлений (`walletId` наш и `sum !== 0`);
  - нормализация телефона;
  - разбор ошибок Syrve (`Validation_IncorrectPhone` → гость не найден);
  - обновление токена (истёк → новый, параллельные запросы → один запрос токена).
- Syrve в тестах — через `MockSyrveClient` или подмену `fetch`, без сети.
- Тест пишется вместе с логикой в той же ветке. `npm test` должен проходить перед PR.
- Формат и поведение Syrve — в `docs/syrve-api-notes.md` (проверено на живом API). Не выдумывай поля; чего там нет — спроси.

## Тестовая организация и секреты

- Работаем только с выданной тестовой организацией.
- Настройки программ лояльности в кабинете Syrve не менять.
- Репозиторий публичный: `apiLogin`, токены, пароли — только в `.env`. Не вставлять их в код, тесты, `docs/api-samples/`, сообщения коммитов.
