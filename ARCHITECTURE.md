# Архітектура

## Частини сервісу

```
 Браузер адміна                                   Telegram
      │                                               ▲
      ▼                                               │ long polling / sendMessage
 admin (nginx) ── статика React                       │
      │  /api/*  (той самий origin, cookie сесії)     │
      ▼                                               │
 api (NestJS, HTTP)                         worker (NestJS, без HTTP)
  ├ Auth      вхід, JWT у cookie, guard      ├ Bot            grammY: реєстрація, картка, історія
  ├ Guests    пошук гостя                     ├ poll  (BullMQ) раз на 30 с: нові транзакції гостей
  ├ Loyalty   нарахування/списання, журнал,   └ notify(BullMQ) надсилання повідомлень
  │           історія                         (спільні модулі: Guests, Loyalty)
  └ Health
        │            спільні: SyrveModule · PrismaModule · ConfigModule            │
        ├──────────────────────────────┬──────────────────────────────────────────┤
        ▼                              ▼                                          ▼
   PostgreSQL                        Redis                               Syrve Cloud API
   (наші дані, outbox)               (черги BullMQ, розклад)             (гості, картки, баланс, транзакції)

 migrate — одноразовий контейнер: prisma migrate deploy; api і worker стартують лише після нього.
```

**Чому два процеси.** Один код (`api/src`), дві точки входу: `main.ts` (api) і `worker.ts` (worker). Бот або поллер зависли —
панель працює; рестарти незалежні. Міграції — окремим кроком: інакше новий код worker міг почати роботу зі старою схемою
(так і сталося під час О6, див. [AI_LOG.md](./AI_LOG.md)).

**Syrve лише через інтерфейс.** Усі HTTP-виклики до Syrve — тільки в `SyrveClient` (`api/src/syrve`). Реалізація обирається
через DI за `SYRVE_MODE`: `RealSyrveClient` (живий API) або `MockSyrveClient` (памʼять процесу). Методи інтерфейсу
повторюють реальні виклики API (`upsertCustomer`, `addToProgram`, `addCard`, …), а не ховають їх за «зручною» абстракцією.

## Що зберігаємо самі, а що беремо з Syrve

**Syrve — джерело правди:** гість, картки, баланс, транзакції. Баланс у нашій БД не зберігається ніде — щоразу читаємо зі Syrve,
інакше він розійдеться зі змінами з каси й кабінету.

**PostgreSQL — лише те, чого в Syrve немає:**

| Таблиця | Що | Навіщо |
|---|---|---|
| `Guest` | Telegram id ↔ гість Syrve, телефон, номер картки (кеш), `lastRevision` | у Syrve немає звʼязку з Telegram і методу «всі гості»; `lastRevision` — курсор поллера сповіщень (`null` — базова точка ще не взята) |
| `Admin` | логін, scrypt-хеш пароля | вхід у панель; записи старих логінів лишаються для журналу |
| `Operation` | ручні операції панелі: хто, коли, сума, причина, статус, ключ ідемпотентності | журнал «хто і чому» і захист від подвійного нарахування |
| `Notification` | outbox сповіщень: транзакція Syrve → статус надсилання | гарантія «одна операція — максимум одне повідомлення», переживає очистку Redis |

**Redis** — лише черги BullMQ і розклад поллера. Втрата Redis нічого не губить: розклад відновлюється раз на хвилину,
а сповіщення, що чекають, заново ставляться в чергу з Postgres.

## Обмін із Syrve

- Токен (`/api/1/access_token`, живе годину) кешується в памʼяті, оновлюється за 5 хв до закінчення; паралельні запити
  чекають один спільний запит токена.
- Тайм-аут запиту — 15 с. Повтор — **лише після 401** (новий токен), один раз. Тайм-аут і мережеві помилки не повторюються:
  нарахування чи списання могло вже застосуватися.
- Помилки → `SyrveApiError` з `httpStatus`, `errorCode`, `correlationId`; у лог — ці поля, назовні — нейтральний текст
  українською. Текст помилки токена відкидається: Syrve повторює в ньому `apiLogin`.
- `revision` транзакцій розбирається з тексту числа одразу в `BigInt` і передається точним числом — без втрати точності після 2^53.

## Потоки

### Реєстрація (О2)

```
/start → Guest з цим telegramId є? → картка
       → «Надіслати контакт» → contact.user_id === from.id → нормалізація телефону (+380XXXXXXXXX)
       → findCustomer(phone)
           нема:  імʼя → upsertCustomer → addToProgram → addCard(10 випадкових цифр, перевірено, що вільний)
           є:     імʼя не питаємо й не перезаписуємо → addToProgram (повтор безпечний) → addCard, якщо карток немає
       → свіжий гість зі Syrve (кошелька немає навіть після program/add → помилка, Guest не зберігається)
       → базова точка сповіщень: остання ревізія історії гостя
       → Guest (upsert за телефоном: той самий номер з іншого Telegram — перепривʼязка) → картка з QR
```

Подвійне натискання: другий виклик реєстрації для того самого Telegram чекає перший — дві картки не видаються.

### Нарахування / списання (О5)

```
форма: idempotencyKey = UUID на відкриття форми
POST /api/guests/:id/operations
 1. INSERT Operation PENDING (унікальний ключ)        конфлікт ключа → повертаємо наявну операцію, Syrve не викликаємо
                                                       той самий ключ з іншою сумою → 409
 2. черга операцій цього гостя (по одній)              два списання з різними ключами не проходять перевірку разом
 3. списання: свіжий баланс зі Syrve                   менше суми / немає гаманця → FAILED, Syrve не викликаємо
 4. topup / chargeoff (коментар: «причина — логін»)
 5. SUCCESS                                            Syrve відповів помилкою або токен не отримано → FAILED
                                                       тайм-аут / мережа → UNKNOWN (не повторюємо, звірка в кабінеті)
```

- id гостя приводиться до нижнього регістру: Syrve приймає будь-який, а в нас це ключ черги й журналу.
- Після рестарту api незавершені `PENDING` → `UNKNOWN` (процес міг упасти й до виклику Syrve, й після).
- Форма при `UNKNOWN` блокується: нова операція — лише окремою кнопкою після звірки в кабінеті.

### Сповіщення (О6)

```
poll (BullMQ, раз на 30 с, фіксований id розкладу)
  для кожного Guest:
    lastRevision = null → базова точка: пройти історію до кінця, зберегти останню ревізію, нічого не надсилати
    інакше: by_revision від lastRevision, усі сторінки по 50 (≤ 20 сторінок за прохід)
      фільтр: наш гаманець і sum ≠ 0  (службові записи й інші програми — ні)
      ОДНА транзакція БД: рядки Notification (PENDING) + новий lastRevision
  усі PENDING → черга notify (jobId = id транзакції)

notify
  PENDING → SENDING (умовний update: хто не захопив — не шле)
  sendMessage «Нараховано N бонусів. Баланс: M» → SENT
    429 або зʼєднання не встановилось       → PENDING, повтор з backoff (5 спроб)
    403 (бота заблоковано), інші 4xx         → FAILED, без повторів
    5xx або обрив без відповіді              → UNKNOWN, без повторів (повідомлення могло дійти)
  SENT не записався → лишається SENDING; при старті worker → UNKNOWN
```

- **Без історії при підключенні:** базова точка береться при реєстрації, а якщо не вдалося — поллером, без повідомлень.
- **Без дублів:** первинний ключ `Notification` = id транзакції; надсилання — лише після захоплення `PENDING → SENDING`;
  повтор — лише коли є доказ, що Telegram повідомлення не прийняв.
- **Без втрат при очищенні Redis:** курсор не зсувається без записаних рядків outbox, а кожен прохід заново ставить `PENDING`.

### Історія (Д1)

Той самий фільтр, що й у сповіщеннях (одна функція `isBalanceChange`). У Syrve немає зворотного порядку `by_revision`, тож
історія гостя проходиться сторінками від початку, а в памʼяті лишаються останні N (бот — 10, панель — 20).

## Стек

| Частина | Вибір | Чому | Альтернатива |
|---|---|---|---|
| Backend | NestJS + TypeScript | модулі й DI дають структуру з коробки; знайомий інструмент | Express — менше шаблонного коду, але структуру тримати самому |
| БД / ORM | PostgreSQL + Prisma | схема читається як документація, міграції в Git | Drizzle — новий інструмент у день тестового |
| Черги | Redis + BullMQ | розклад, ретраї з backoff, `jobId` проти дублів у черзі | `setInterval` — губить стан, не ретраїть |
| Бот | grammY (+ вбудований `session`) | TypeScript з коробки; плагін `conversations` не знадобився | Telegraf — слабші типи |
| QR | `qrcode` | генерується локально — номер картки не йде стороннім сервісам | зовнішній сервіс QR-картинок |
| Адмінка | React + Vite, без UI-кіту й роутера | внутрішня панель, SSR не потрібен | Next.js — зайва складність |
| Проксі | nginx | статика + `/api` з одного origin: без CORS, cookie працюють; ліміт входу | окремі порти + CORS |
| Авторизація | `@nestjs/jwt` у httpOnly cookie, пароль — `crypto.scrypt` | scrypt вбудований у Node — без нативної збірки bcrypt на Alpine; cookie `httpOnly`, `sameSite=lax`, `Secure` за HTTPS | bcrypt, сесії в Redis |
| Валідація | class-validator (DTO) + zod (`.env`) | рідний шлях Nest; кривий `.env` — падіння на старті з назвою змінної | лише zod |
| Тести | Jest (ts-jest) | стандарт для Nest; unit на критичну логіку | Vitest |
| Запуск | Docker Compose | усе однією командою, міграції окремим кроком | ручний запуск |

## Особливості Syrve, які вплинули на код

Перевірено на живому API тестової організації; деталі й приклади — [docs/syrve-api-notes.md](./docs/syrve-api-notes.md).

- **4 програми лояльності** в організації → `SYRVE_PROGRAM_ID` і `SYRVE_WALLET_ID` явно в `.env`; `programId ≠ walletId`.
- **У гостя 3 гаманці** → баланс лише з гаманця `SYRVE_WALLET_ID`, не перший у списку.
- **Syrve пускає списання в мінус** (списання 500 при балансі 0 → −500, відповідь 200) → перевірка балансу до `chargeoff`.
- **«Гостя не знайдено» — HTTP 400** зі своїм `errorCode` для кожного типу пошуку (`Validation_IncorrectPhone`,
  `Card_CanNotFindByNumber`, `Customer_CustomerNotFound`) → `null` лише для свого коду, решта — помилка.
- **`create_or_update` — upsert за телефоном** і може перезаписати імʼя → спершу `findCustomer`.
- **Повтор `program/add` безпечний** (той самий гаманець, баланс не змінюється).
- **В організації є чужі гості** з 10-значними картками → номер картки перевіряємо на зайнятість.
- **`by_revision`:** межа не включається, порожня сторінка повертає запитану ревізію, «ревізія з майбутнього» повертається
  як є → поточну ревізію без обходу історії не дізнатись.
- **Службові транзакції** (`SetGuestCategory`: `sum 0`, `walletId null`) → фільтр для сповіщень та історії.
- Типи наших операцій: з API — `RefillWalletFromApi` / `WithdrawWalletFromApi`, з кабінету — `RefillWallet`.
- **Два формати помилок:** `{ correlationId, errorDescription, error? }` і для лояльності `{ code, errorCode, message }`.
